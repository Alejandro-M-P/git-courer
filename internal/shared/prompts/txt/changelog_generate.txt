## Rules for user-friendly language

### 1. What's the USER PROBLEM this solves?

Bad: "add CSV export to reports"
Good: "Export reports to Excel/CSV — share data with your team"

Bad: "add rate limiting to login"
Good: "Your account is protected from brute-force attacks"

Bad: "improve query performance"
Good: "Search results load in under 500ms — no more waiting"

### 2. Use concrete SYMPTOMS, not technical fixes

Bad: "fix nil pointer crash in user list"
Good: "The app no longer crashes when a project has no users"

Bad: "fix memory leak in cache"
Good: "App stays fast even after using it for hours"

### 3. Bug Fixes: reason about the OUTCOME, not the words

For each fix:, ask yourself: "What problem does this solve for the user?"

A fix is user-facing if it:
- Enables a capability that was broken before
- Prevents a failure mode the user would see
- Removes silent failures or cryptic errors

Technical words like "timeout", "stderr", "authentication" in a commit message
are NOT signals to skip — they often mean "this thing now works properly" → USER-FACING.

Examples of USER-FACING fixes:
- "fix: handle gh release timeout" → enables GitHub releases → USER-FACING
- "fix: require GitHub CLI authentication" → prevents silent failures → USER-FACING
- "fix: handle nil pointer in user list" → prevents crash → USER-FACING

Examples to SKIP:
- "fix: refactor error variable naming" → only internal cleanup
- "fix: update test coverage" → only affects tests
- "fix: internal refactor" → explicitly internal

The key question: Would a user notice or benefit from this fix?
If yes → include it. If only developers care → skip.

### 4. Skip anything only a developer cares about
Skip: refactor, internal, tests, docs updates, dependency bumps
UNLESS: it fixes a security issue users need to know about

### 4. Be specific about WHERE in the app

Bad: "You can now invite team members"
Good: "Add team members from Settings → Team Members"

### 5. Use everyday language

Bad: "User authentication improved"
Good: "Login is now more secure"

Bad: "Project configuration enhanced"
Good: "Configure projects faster with the new settings panel"

## Breaking changes

A commit is breaking ONLY if it contains:
- `!` after the type (feat!:, fix!:) OR
- The exact text `BREAKING CHANGE:`

If breaking: explain WHAT THE USER MUST DO, not just what changed.

Bad: "BREAKING CHANGE: config format changed"
Good: "Update your config files to the new format — see migration guide"
